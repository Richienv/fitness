# Chinese nutrition labels

Use **Scan label nutrisi** directly from the meal page or food builder. The camera has a 4:5 portrait preview with table-placement hints. Its actual crop follows the inner guide (plus a small edge margin), accounting for object-fit: cover. The camera reads continuously: a complete reading with a known reference basis, weakest relevant cell confidence of at least 92%, and no warning can open review immediately. Other complete readings need two consistent core readings; partial readings need three and at least two core nutrients. Missing optional rows do not reset core confirmation; conflicting optional values are left blank with a warning. The user reviews, names, edits and adds the food. An image file uses the same OCR and review flow. No food is automatically saved.

Recognition uses the official PaddleOCR.js 0.4.2 SDK with PP-OCRv5 mobile detection and recognition models in a browser worker. `scripts/prepare-ocr.mjs` bundles a worker-only client, excludes the unused main-thread OpenCV import, copies the complete official worker and matching ONNX Runtime 1.24.3 files, and downloads SHA-256-pinned official model archives. The SDK-version guard requires revalidation before changing that build optimization. All runtime assets are served from `/ocr/paddle-v1` by this app with a one-day public cache; change the namespace or client filename when replacing pinned assets. Photo pixels remain on-device; no OCR account, cloud key or paid API is required. The first load still downloads substantial recognition assets. Generated assets are ignored by Git and prepared by both app builds and local development.

The engine initializes while the user positions the label. Leases share one engine, serialize predictions, and release it after 90 seconds of inactivity to speed consecutive scans without keeping models forever. Camera scans start at detection size 768, escalating to 960 when a partly recognized table needs clarification. Uploaded images use 960. The review flags unclear nutrient rows, energy/macronutrient inconsistencies and contradictory readings without changing uncertain numbers automatically.

## Adaptive image preprocessing

The original guide crop/upload is read first. A complete reading with core-cell confidence of at least 85%, no amount inconsistency/unclear-row warning and no unassigned amount row skips rescue inference. An unreadable reference header alone requires human confirmation rather than repeated filtering. Auto mode chooses at most two additional presets for uploads and one per camera frame, based on luminance range, brightness and edge activity. Its 4500 ms upload / 2500 ms camera budget is a soft admission limit for starting another pass, excluding initialization; it cannot interrupt an inference already running. A difficult image can therefore take longer than the original-only path. Manual selection compares the original with exactly one chosen filter. Each rescue is generated lazily from original pixels, never by repeatedly filtering an already modified image.

Available presets: bounded percentile auto-contrast in color; grayscale with contrast/brightness correction; a light Gaussian denoise with isolated-noise suppression and bounded sharpening; adaptive local-mean black-and-white thresholding. Thresholding is available manually; it is excluded from automatic selection because the initial labeled-photo test showed lost glyphs without recovery. Transparent images are composited onto white. Aspect ratio is preserved and the existing camera guide crop and bounded 1200×1500 canvas are reused. Model-specific pixel normalization remains inside the official SDK using its model configuration; preprocessed images stay 8-bit RGB/RGBA to avoid normalizing twice.

Selection uses nutrient completeness, reference basis, plausible amounts and OCR confidence. Impossible sugar/fat/mass relationships and energy inconsistencies are penalized. Equal scores preserve the original. Nutrient values are not blended across variants. Differing values or bases trigger a review hint. Displayed confidence is OCR recognition confidence, not a calibrated probability that the nutrition is correct. The result identifies the class (nutrition table or incomplete label), winning method, original/selected previews and per-variant predictions in expandable details.

The console emits only method, confidence, pass count and timing for each scan; it does not persist or send photos, names, text or nutrition values. `tsx scripts/nutritionPreprocessEval.ts <labeled-results.json>` compares original and selected results using per-field accuracy, precision, recall, exact case count, independent reference-basis accuracy and mean warm pipeline latency. Wrong returned numbers count as both an incorrect return and a missed true value. Test with distinct labeled packages, including low light, glare and blur; derivatives of one photo are a smoke test, not evidence of generalization. No model training or fine-tuning is performed.

The parser joins detected cells along the table's slanted rows, then maps Chinese and English nutrient labels. It uses explicit amount units; it never uses NRV percentages as amounts. kJ is divided by 4.184 to produce kcal. Sodium is stored in mg, other optional nutrients in g. Saturated and trans fat stay separate from total fat. Salt and sodium stay separate; sodium × 2.5 / 1000 is displayed as a salt-equivalent explanation, without filling an unobserved salt field. Unknown nutrients remain blank. An unknown reference basis requires a user selection.

Per 100 g/ml and per serving are supported. The review form scales all nutrients to the entered consumed amount. Sugar, sodium, salt, saturated fat, trans fat and fiber survive the tray, meal JSON, server import and recipe composition. Existing meals and catalogue records require no migration.

The supplied sample label declares per 100 g: energy 2228 kJ (532.5048 kcal), protein 8.2 g, total fat 28.6 g, saturated fat 16 g, trans fat 0 g, carbohydrates 60.6 g, sugar 18 g and sodium 251 mg. Its salt amount is not declared.

OCR quality depends on legibility. Glare, folds, severe perspective and blur can omit or misread fields; the review form remains mandatory. A browser test with a static image camera fixture verifies the automatic loop and actual OCR, but does not substitute for testing the physical phone camera.
